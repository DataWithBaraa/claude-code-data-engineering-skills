01

Root cause

The file delivered by the source commerce, 2026-08-19.jsonl, has a new schema: the column status_code is called status. The orders cleaning step in the silver layer, commerce/orders.sql, still reads the column as status_code. The name is no longer in the file, so the step fails and the gold tasks are skipped.

2026-08-18 · before 
"row": {
    "status_code": 40,
    "channel": "app"
}
2026-08-19 · after 
"row": {
    "status": 40,
    "channel": "app",
    "sales_channel": "web"
}

04

Solutions

Solution 1

Fix the schema

3 hours · recommended
  • In the commerce data contract, map the source's new name status to the column status_code. The old name stays accepted, so a resend in schema version 1 also loads.
  • Regenerate the bronze step and the orders cleaning step from the data contract. Silver and gold keep the column name status_code, so nothing changes for consumers.
  • sales_channel stays in bronze until commerce defines it.
  • Rerun the daily job for 2026-08-19.
Solution 2

Check the schema at gate 1

2 days
  • Before any data is loaded, gate 1 compares the columns of the file with the contract.
  • A new column stays in bronze and is reported. The job does not fail.
  • An unlisted rename quarantines the file at gate 1, with a message naming the column that changed.
  • A rename listed in the contract passes gate 1 without a code change.
05

Future risks

  • A source can rename a column in any delivery.
  • Until Solution 2 is deployed, a rename in any of the 16 commerce tables fails the same way: their cleaning steps read columns by name.
  • The CSV files and the finance workbook would not fail this way: their columns are checked against the contract before anything loads.
